# PR #61: Claude Code harness layering

Source review on 2026-10-25, pinned to PR head `6112bd9ae6b6f28d0f40a426b07eabca723e602f`. No PR code was executed for this review.

## Finding

PR #61 places the Claude Code runtime inside LearnHarness's existing Pi agent loop, but deliberately removes much of the normal coding-agent configuration. Pi does not automatically strip Claude Code: the provider's explicit CLI flags do that work. This is an adapter around a native agent runtime, not a direct Claude model transport. [Launch configuration](https://github.com/Ivanko1608/learnharness/blob/6112bd9ae6b6f28d0f40a426b07eabca723e602f/src/agent/claude-code/stream.ts#L82-L109)

LearnHarness uses the `pi-ai` and `pi-agent-core` libraries, not the full `pi-coding-agent` application and extension host. The PR author explains this distinction when discussing an existing external bridge. Therefore describing the design as two complete coding assistants independently working on the same task would overstate the duplication. [Author's explanation](https://github.com/amosblomqvist/learnharness/pull/61#issuecomment-6388309466)

## Limits and engineering judgment

Disabling the coding tools and replacing the prompt does not remove every native runtime behavior. The launch configuration does not explicitly disable or synchronize Claude Code auto-compaction, while its parser accepts selected stream events and ignores other line types. Native context changes could therefore differ from the application's stored transcript. This is a design concern inferred from source, not a reproduced failure. Current Claude Code documentation also notes that its `EndConversation` tool can remain when MCP tools are present, so `--tools ""` should not be described as eliminating literally every native behavior. [Launch flags](https://github.com/Ivanko1608/learnharness/blob/6112bd9ae6b6f28d0f40a426b07eabca723e602f/src/agent/claude-code/stream.ts#L82-L109), [Event filtering](https://github.com/Ivanko1608/learnharness/blob/6112bd9ae6b6f28d0f40a426b07eabca723e602f/src/agent/claude-code/cli-events.ts#L154-L181), [Context management](https://code.claude.com/docs/en/how-claude-code-works#when-context-fills-up), [CLI reference](https://code.claude.com/docs/en/cli-reference)

The engineering tradeoff is defensible: retain LearnHarness's teaching semantics while using the installed subscription-capable CLI. It also adds two runtime lifecycles, streaming translation, held MCP requests, timeouts and transcript reconstruction. Keeping a process alive can avoid repeated startup and replay within a tool sequence; actual cache or allowance savings require measurement. The PR discussion reports tests around answers before/after the idle timeout but is not independent verification here. [Idle-timeout follow-up](https://github.com/amosblomqvist/learnharness/pull/61#issuecomment-6390731574)

The fork's PR #94 has the same general layering through ACP. Its implementation starts a fresh native session per model round, requests disabled built-in tools/settings/persistence, cancels after capturing a tool request, then lets Pi execute the tool and replay its result next round. PR #61 instead keeps the CLI process waiting across compatible tool results. Neither design is a direct model transport with the native agent runtime removed. [PR #94 engine](https://github.com/Yawsom/learnharness/blob/6380e833792dfdc4f05521f9769ccc99742a119a/src/agent/acp/engine.ts#L138-L169)

This comparison describes PR #94 at commit `6380e83`. Its subsequent [ACP session reuse implementation](acp-session-reuse.md) retains native sessions across compatible tool results while preserving Codex's verified ephemeral-thread requirement. The launch flags, ownership and runtime distinction above remain relevant; the earlier per-tool startup/replay limitation is addressed by that follow-up.
