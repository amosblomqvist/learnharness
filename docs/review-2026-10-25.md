# Adversarial review — ACP subscriptions and repository

Reviewed on 2026-10-25 against `6cba9c8c5afe8a63f47ea4ebae6e91d8a205cebb` (0.3.4), including all tracked working-tree changes and untracked production/test files. Five independent reviewers covered standards/architecture, feature correctness, security, desktop/packaging, and runtime/data integrity. The originating request was to add Codex and Claude Code ACP subscription connections using installed adapters, integrate setup/model slots/structured tools, and fix desktop data/tracing checks.

**Status: nine ACP-related findings are fixed; four independent repository findings remain open** (RUN-01, RUN-02, RUN-03, DESK-03). The original register contains five introduced and seven pre-existing findings; subsequent user testing added ACP-03, a sixth introduced issue. This remediation covers the subscription path and its security, Windows startup, accounting and native-history dependencies. Original evidence/locations below describe the reviewed version; the resolution notes describe the current working tree.

P1 means high priority before release, P2 means a functional or contract defect to fix, and P3 means a lower-impact reporting or feedback defect. No P0 was reported.

## Security

### SEC-01 — Unauthenticated web configuration can launch arbitrary processes

**Resolution:** Fixed. ACP mutations and engine resolution require the loopback local app mode. Missing/cross-origin requests are rejected. Connect accepts only an empty object; executable/argv authority comes from a host-owned file or installed adapter defaults, and HTTP-writable legacy command fields are ignored. Regression checks cover public mode, missing Origin, supplied executable/args, and a malicious saved executable.

- **Location:** [`app/api/acp/[id]/route.ts`](../app/api/acp/[id]/route.ts), lines 9–20; [`src/server/acp.ts`](../src/server/acp.ts), lines 33–38; [`src/agent/acp/client.ts`](../src/agent/acp/client.ts), lines 84–86.
- **Trigger and impact:** A network client can reach a web deployment, send an Origin-absent JSON connection request, and select the executable and arguments. The client process starts before ACP/subscription verification, so a failed handshake does not prevent OS execution as the server user. `npm start` uses Next's default all-interface listener, and the ACP documentation supports web deployments. This adds a process-execution primitive to the existing unauthenticated API.
- **Evidence:** Source-level tracing from route validation through `connectAcp` to subprocess creation, plus the installed Next CLI's listener default. No live exploitation was required or established. Electron explicitly binds loopback; a remote desktop/browser-origin bypass was not demonstrated.
- **Fix direction:** Authenticate and authorize this privileged configuration surface, or move executable selection to trusted host configuration. Define and enforce the deployment boundary independently of caller-controlled headers.
- **Closure check:** Unauthenticated network requests cannot start any executable, even when the requested adapter would fail initialization. Authorized local setup still supports approved custom executable paths.

### SEC-02 — Generated SVG enters the executable application DOM

**Resolution:** Fixed. Both figure renderers use the shared inert SVG image boundary. Generated markup never enters the application DOM. Card/fullscreen regressions exercise scripts, foreignObject HTML, event handlers, javascript links and external image references; ordinary figure sizing is retained.

- **Location:** [`components/artifacts/visual-card.tsx`](../components/artifacts/visual-card.tsx), lines 27–32, 129, and 159; [`components/session-overlay.tsx`](../components/session-overlay.tsx), lines 87–94 and 279–286.
- **Trigger and impact:** An attacker-influenced generated figure reaches the viewer. Inline rendering uses incomplete regex filtering; opening fullscreen passes the original SVG to an unfiltered HTML sink. Active event attributes or embedded HTML can therefore run in the application's origin, where study APIs and the ACP configuration surface are available.
- **Evidence:** Both source-to-sink paths were inspected. The visual-maker's PNG verification checks appearance, not markup safety. The isolated browser execution probe could not start in the sandbox and was cleaned up; this finding is supported by source inspection, not a successful live exploit.
- **Fix direction:** Render figures as inert images or apply a strict parser-based SVG allowlist consistently at every sink, including fullscreen.
- **Closure check:** Active markup and external resource constructs cannot execute or access the app origin through either the inline card or fullscreen viewer. Ordinary diagrams still display correctly.

## Feature correctness

### ACP-01 — Disconnected ACP pins strand background jobs

**Resolution:** Fixed. Engine resolution errors use the runner's existing failure-result/refusal path. The disconnected-ACP regression delivers exactly one failure steer and finalizes the job as error rather than leaving it running.

- **Location:** [`src/server/acp.ts`](../src/server/acp.ts), lines 20–21; [`src/agent/subagents/runner.ts`](../src/agent/subagents/runner.ts), line 204; engine injection in [`src/server/chat-handler.ts`](../src/server/chat-handler.ts).
- **Trigger and impact:** Keep Strong on a working provider, pin Cheap or Vision to Codex, disconnect Codex, then dispatch a background job using that slot. Disconnect intentionally preserves pins. `engineForSpec` throws before the runner's refusal/finalization handling; its caller discards the rejected promise. The job remains `running`, receives no failure steer, and can cause an unhandled rejection.
- **Evidence:** An isolated probe using the real factories and mocked settings/ports returned a disconnected error with `status: "running"`, no updates, and zero steers. No inference or user data was involved.
- **Fix direction:** Catch engine-resolution failures and route them through the existing refusal/result delivery path.
- **Closure check:** Dispatch and stale-job recovery with a disconnected pinned provider settle honestly, deliver one failure result, and leave no unhandled rejection or permanently running job.

### ACP-02 — Reported Codex reasoning tokens are discarded

**Resolution:** Fixed. Native thoughtTokens is captured as reasoning and retained in application accounting. The real-stdio fixture asserts measured reasoning = 11 while total tokens remain 194, with no double-counting.

- **Location:** [`src/agent/acp/engine.ts`](../src/agent/acp/engine.ts), lines 25–38.
- **Trigger and impact:** Codex reports measured `usage.thoughtTokens`, but `PromptResult` and `recordUsage` omit that field. Existing collectors consequently persist reasoning as zero.
- **Evidence:** [Codex ACP 2.2.2's primary implementation](https://github.com/agentclientprotocol/codex-acp/blob/v2.2.2/src/TokenCount.ts#L47-L55) emits the field; the adapter-to-pi mapping does not consume it. The primary-source review also confirmed cached counters are disjoint, so summing the existing input/output/cache fields is correct.
- **Fix direction:** Map reported thought tokens to pi's reasoning usage while retaining output totals unchanged and preserving reporting presence.
- **Closure check:** A fixture reporting reasoning tokens persists the measured value without adding it a second time to total/output tokens.

### ACP-03 — Internal replay rounds appear as separate Codex app chats

- **Trigger and impact:** Every model/tool round starts a fresh native session and sends the saved lesson as its first prompt. The installed Codex ACP adapter creates an ordinary persistent thread, so each internal replay becomes another Codex sidebar chat.
- **Evidence:** The user's sidebar screenshot and 12 matching stored chats with LearnHarness temporary working directories. An offline native-CLI fixture reproduced persistence on each fresh ACP round before the fix.
- **Resolution:** `codex-ephemeral.cjs` uses the adapter's supported `CODEX_PATH` boundary to enforce `ephemeral: true` on native thread creation. `AcpClient.newSession` requires the proxy's matching acknowledgement before prompting. Existing native login and the adapter's bundled CLI version are retained. Twelve matching inactive replay chats were archived through the Codex app tool; none remained in the active chat inventory afterward.
- **Verification:** The history regression first failed on both stored-chat creation and ignored ephemeral mode. All four history tests now pass, including compatible CLI resolution and refusing adapters that bypass the proxy. The real installed adapter confirmed an ephemeral session and discovered eight catalog entries (seven named models plus default), without inference.
- **Follow-up checks:** The 37-test ACP regression group passed. The rebuilt standalone app also connected successfully with the required ephemeral acknowledgement and retained seven named models and the saved lesson. Its native proxy is included in the curated payload.
- **Live acceptance:** One minimal Codex subscription prompt returned `OK` in confirmed ephemeral mode. Its thread ID was absent from the active Codex chat inventory afterward, and no internal replay chats remained there. Both Node/Electron payload smoke checks, lint and typecheck passed after rebuilding.

## Runtime and data integrity

### RUN-01 — Compaction can overwrite a live turn's saved response

- **Location:** [`src/server/compaction.ts`](../src/server/compaction.ts), lines 169–171 and 214–226; [`src/server/chat-handler.ts`](../src/server/chat-handler.ts), lines 228–241 versus the live-turn gate at 285.
- **Trigger and impact:** A first request persists input that crosses the compaction threshold and starts its live turn. A second POST can enter compaction before it is rejected as a concurrent turn. Compaction snapshots the messages, awaits a summary, and then writes the old snapshot plus its marker, potentially erasing the first turn's subsequently saved response.
- **Evidence:** With in-memory stores, the probe held summarization, persisted the live assistant response, then released summarization. The response existed before compaction completed and was absent afterward.
- **Fix direction:** Acquire/check turn ownership before compaction and validate or re-read the record before appending the marker; do not replace newer messages with an earlier snapshot.
- **Closure check:** Exercise the interleaving above and a threshold change during a live turn. Both the assistant response and compaction marker remain durable, with one conversation turn at a time.

### RUN-02 — An aborted audit waiter lets successors bypass the lock holder

- **Location:** [`src/agent/subagents/extraction.ts`](../src/agent/subagents/extraction.ts), lines 879–905, especially 899–904.
- **Trigger and impact:** A holds the audit/merge lock, B waits, and B is aborted. B's `finally` resolves its tail immediately even though A still owns the critical section. C can then audit and merge against a graph A is still changing, undermining serialized identity decisions and allowing duplicate nodes.
- **Evidence:** A public-pipeline probe with faux engines and in-memory ports held A's auditor, aborted B while waiting, and observed C audit and finish merging before A was released. The existing abort test starts C only after A finishes and misses this ordering.
- **Fix direction:** Preserve predecessor ordering for canceled tickets while returning the caller's abort promptly; a canceled waiter must not unlock its predecessor.
- **Closure check:** Hold A, queue and abort B, then queue C. C cannot read/audit/merge until A releases, and subsequent tickets continue without deadlock.

### RUN-03 — Result and abort steers can persist under the same ID

- **Location:** [`src/server/jobs.ts`](../src/server/jobs.ts), lines 194–220 and 375–388.
- **Trigger and impact:** A job result is handed to a live agent, then the learner aborts before the next steering boundary. The handed result is retained, while an abort steer is enqueued under the same deterministic ID. The agent and record can contain both a completed result and an assertion that no result is coming, with duplicate message/UI keys.
- **Evidence:** In-memory job/store probes observed both handoffs. Production `toLlmMessages()` retained the contradictory messages, and `persistTurn()` stored both markers with the same ID; there is no downstream coalescing.
- **Fix direction:** Coalesce by steer ID and honor the documented past-recall policy once a result has been handed to the agent.
- **Closure check:** Interleave delivery and abort at the handoff boundary. Exactly one coherent result/abort event reaches the model and persistent transcript for each steer ID.

## Desktop and packaging

### DESK-01 — Exited adapters can leave descendant processes running

**Resolution:** Fixed. Windows starts a worker inside a kill-on-close Job Object before it can launch an adapter. A separate keeper owns the handle, so adapter/wrapper exit and host shutdown still terminate descendants. POSIX cleanup always addresses its owned process group, including after leader exit. Windows normal/abort/exited-leader tests pass; native POSIX execution was unavailable.

- **Location:** [`src/agent/acp/client.ts`](../src/agent/acp/client.ts), lines 214–225.
- **Trigger and impact:** An adapter or wrapper exits before `close()`, but a descendant continues running. The disposal guard skips all process-tree termination once the immediate child has an exit code or signal. Cleanup completes while owned work can remain alive.
- **Evidence:** A disposable Windows `.cmd` fixture started a background Node descendant, answered initialization, and exited with code 1. The descendant was alive before and after awaited cleanup. Only that fixture PID was terminated afterward, and its temporary files were removed. The POSIX group-leader case follows from the same source guard; native POSIX execution was unavailable.
- **Fix direction:** Own the tree independently of the leader's lifetime: terminate the owned POSIX group after leader exit, and use Windows Job Object ownership or an equivalent mechanism.
- **Closure check:** Crash/exit the adapter leader while a descendant remains. Cleanup must stop all owned processes on both Windows and POSIX without touching unrelated processes.

### DESK-02 — Desktop dev and test commands use incompatible Windows env syntax

**Resolution:** Fixed. Portable Node scripts replace POSIX environment assignments in npm test and desktop:dev. A foreground npm run app launcher opens the prepared local profile on loopback and prints the URL and stop instructions. The Windows npm test path is exercised by the regression runs.

- **Location:** [`package.json`](../package.json), lines 19 and 22.
- **Trigger and impact:** Run `npm run desktop:dev` or `npm test` under a default Windows setup. Their POSIX `NAME=value command` syntax is rejected by `cmd.exe`; the desktop command's `concurrently -k` then kills the accompanying Next process.
- **Evidence:** Installed concurrently documentation identifies `cmd.exe` as the Windows default. A harmless assignment probe returned that `LH_DEV_URL` was not recognized as a command.
- **Fix direction:** Use a portable Node launcher or cross-platform environment assignment.
- **Closure check:** Both commands work from default Windows PowerShell/npm and POSIX shells without requiring a customized npm script shell.

### DESK-03 — Manual update checks are silent when already current

- **Location:** [`electron/main.cjs`](../electron/main.cjs), lines 427–428.
- **Trigger and impact:** Manually check for updates when the installed version is current. The code treats missing `updateInfo.version` as the no-update signal, but the installed updater returns populated update metadata together with `isUpdateAvailable: false`, so the intended confirmation dialog never appears.
- **Evidence:** Installed electron-updater 6.8.9's response shape was inspected; an isolated invocation using that shape produced zero dialogs.
- **Fix direction:** Check `result.isUpdateAvailable` when deciding whether to show the already-current response.
- **Closure check:** Manual checks give appropriate feedback for no update, available update, and error responses; automatic checks remain unobtrusive.

## Standards and architecture

### STD-01 — Unreported ACP usage becomes fabricated zero counts

**Resolution:** Fixed. Serializable reported-counter metadata accompanies pi's required internal numeric counters. Chat, jobs, extraction and compaction project it through one pure accounting helper. Missing counters remain absent; reported zero and positive reasoning stay measured, including after JSON serialization.

- **Location:** [`src/agent/acp/engine.ts`](../src/agent/acp/engine.ts), lines 30–38 and 59–64; [`src/core/contracts/chat.ts`](../src/core/contracts/chat.ts), lines 117–130; [`docs/architecture.md`](architecture.md), line 456.
- **Trigger and impact:** An ACP reply omits usage entirely or omits individual counters. The engine initializes all fields to zero and maps missing counters to zero, so persistence/UI cannot distinguish unreported usage from measured zero usage. This violates the documented absence contract.
- **Evidence:** The existing offline `permission` fixture returned no usage; the completed assistant message nevertheless contained numeric zeros for every counter, which collectors copy into `CallUsage`.
- **Fix direction:** Preserve reporting presence through the adapter/accounting seam so application records retain absent counters. Accommodate pi's internal numeric usage requirements without treating internal defaults as measured app usage.
- **Closure check:** Test missing, partial, measured-zero, and measured-positive usage separately. Only reported fields appear as measured counts in persistent records and UI.

### STD-02 — Usage-write failures prevent turn cleanup

**Resolution:** Fixed. Accounting append failures are contained, and post-persistence turn cleanup runs in finally. The failure-injection test retains the answer, clears liveness and the running handle, and accepts another input.

- **Location:** [`src/server/chat-handler.ts`](../src/server/chat-handler.ts), lines 475–482 and 504–515; [`docs/architecture.md`](architecture.md), line 455.
- **Trigger and impact:** The assistant transcript persists successfully, then the secondary `appendTurnUsage` write throws. Execution never reaches `endTurn`, `unregisterTurn`, or later settlement. A completed chat remains busy until timeout/restart, violating failure containment.
- **Evidence:** An in-memory-store/faux-engine probe returned HTTP 200 and retained the assistant response, but both the liveness flag and completed turn handle stayed registered.
- **Fix direction:** Contain usage failures separately and guarantee registry/steer cleanup with `finally`, while preserving transcript-before-settlement ordering.
- **Closure check:** Inject a usage-write failure after transcript persistence. The response stays durable, the turn is no longer running, handles are released, and the next input can proceed.
